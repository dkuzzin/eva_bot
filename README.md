# EVA - Event Volunteer Assistant

EVA - чат-бот с Mini App в MAX для создания мероприятий, регистрации волонтеров и управления участниками.

**Организатор** создает мероприятие прямо в MAX, задает основную информацию и собственную форму регистрации, после чего может поделиться мероприятием с другими пользователями.
**Участник** открывает мероприятие в MAX, заполняет форму и регистрируется.

Организатор может просматривать свои мероприятия, видеть зарегистрированных участников и выгружать список в CSV. Участник может просматривать свои регистрации и отменять их.

*Один пользователь MAX может одновременно выступать организатором одних мероприятий и участником других. Регистрация на собственное мероприятие также допускается.*

## Основной пользовательский сценарий

1. Организатор открывает EVA в MAX.
2. Через Mini App создает мероприятие:
    - указывает название и описание;
    - задает дату и время;
    - указывает место проведения;
    - при необходимости задает ограничение количества участников;
    - добавляет поля регистрационной формы.
3. EVA сохраняет мероприятие в PostgreSQL.
4. Организатор открывает созданное мероприятие и может поделиться им в MAX.
5. Участник открывает мероприятие.
6. Mini App показывает информацию о мероприятии и регистрационную форму.
7. Участник заполняет форму и отправляет регистрацию.
8. Backend проверяет ограничения мероприятия и сохраняет регистрацию вместе с ответами формы.
9. Участник может открыть список своих регистраций и отменить регистрацию.
10. Организатор может открыть список своих мероприятий.
11. Для конкретного мероприятия организатор может посмотреть зарегистрированных участников.
12. При необходимости список участников можно скачать в формате CSV.
13. Организатор может отменить мероприятие. Оно сохраняется в системе со статусом `CANCELLED`, а существующие регистрации не удаляются.

## Состав решения

Проект состоит из следующих компонентов:

- MAX Bot на Go
- MAX Mini App на React и TypeScript
- Backend API на Java и Spring Boot
- PostgreSQL
- Docker Compose для запуска сервисов приложения
- Nginx на VPS для HTTPS-доступа и reverse proxy

## Архитектура

MAX Bot отвечает за взаимодействие с MAX: обработку команд пользователя, запуск Mini App и сценарии распространения мероприятий.

Mini App предоставляет интерфейс для создания и просмотра мероприятий, регистрации участников и работы организатора со своими мероприятиями.

Java Backend содержит бизнес-логику приложения:
- создает и хранит мероприятия;
- проверяет данные запросов;
- управляет регистрациями;
- контролирует ограничение количества участников;
- проверяет состояние мероприятия;
- проверяет права владельца;
- формирует список зарегистрированных участников;
- экспортирует регистрации в CSV.

PostgreSQL используется для постоянного хранения мероприятий, полей регистрационных форм, регистраций и ответов пользователей.

Сервисы `miniapp`, `server`, `bot` и PostgreSQL запускаются через Docker Compose.

Nginx работает на VPS вне Docker Compose и принимает внешний HTTP/HTTPS-трафик.

Используются следующие адреса:

- `https://eva.chernushka.fun` - Mini App;
- `https://api.chernushka.fun` - Java Backend;
- `https://bot.chernushka.fun/webhook` - webhook MAX Bot.

HTTPS обеспечивается Nginx с сертификатами Let's Encrypt.

Подробная инструкция по развертыванию находится в [`deploy/nginx/README.md`](deploy/nginx/README.md).

## Backend API

Backend предоставляет HTTP API для работы с мероприятиями и регистрациями.

### Мероприятия

- `POST /api/events` - создать мероприятие;
- `GET /api/events` - получить мероприятия, созданные текущим пользователем (сортируются по дате начала);
- `GET /api/events/{eventId}` - получить информацию о мероприятии;
- `PATCH /api/events/{eventId}/cancel` - отменить мероприятие (статус `CANCELLED`).

### Регистрации пользователя

- `POST /api/events/{eventId}/registrations`  - зарегистрироваться на мероприятие;
- `GET /api/events/{eventId}/registrations/me` - получить свою регистрацию на конкретное мероприятие;
- `DELETE /api/events/{eventId}/registrations` - отменить свою регистрацию;
- `GET /api/registrations/me` - получить все свои регистрации вместе с краткой информацией о мероприятиях.

Backend не допускает повторную регистрацию одного пользователя на одно мероприятие и проверяет доступность свободных мест.

Регистрация разрешена только на мероприятия со статусом `OPEN`.

### Работа организатора с участниками

- `GET /api/events/{eventId}/registrations` - получить список зарегистрированных участников и их ответы на регистрационную форму;
- `GET /api/events/{eventId}/registrations/export` - скачать список зарегистрированных участников в формате CSV.

Эти операции доступны только владельцу мероприятия.


Полный контракт Backend API описан в [`openapi.yaml`](openapi.yaml).

Сценарий воспроизводимой проверки API описан в [`DATA-API.yaml`](DATA-API.yaml).

Production URL Backend API:

```text
https://api.chernushka.fun
```

Для запросов, зависящих от текущего пользователя, используется HTTP-заголовок:

```
X-Max-User-Id
```

`GET /api/events/{eventId}` доступен без этого заголовка.

## Формат ошибок API

Backend возвращает ошибки в JSON.

Пример:

```json
{
  "code": "ALREADY_REGISTERED",
  "message": "User is already registered"
}
````

Для ошибок валидации дополнительно возвращается объект `fields`:

```
{
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "fields": {
    "title": "не должно быть пустым"
  }
}
```

Основные коды ошибок:

```
VALIDATION_ERROR

INVALID_EVENT_TIME_RANGE
EVENT_STARTS_IN_PAST
EVENT_NOT_FOUND
EVENT_ACCESS_DENIED
EVENT_ALREADY_CANCELLED

INVALID_REGISTRATION_FORM
DUPLICATE_FORM_FIELD
FORM_FIELD_DOESNT_EXIST

EVENT_NOT_OPEN
EVENT_CAPACITY_FULL
ALREADY_REGISTERED
REGISTRATION_NOT_FOUND

DATA_INTEGRITY_VIOLATION
```

Полный контракт ошибок и HTTP-статусов описан в [`openapi.yaml`](openapi.yaml).


## Работа с данными

Backend хранит следующие основные сущности:

- `Event` - мероприятие;
- `FormField` - поле регистрационной формы;
- `Registration` - регистрация пользователя;
- `RegistrationAnswer` - ответ пользователя на поле регистрационной формы.

Данные хранятся в PostgreSQL.   

Схема базы данных создается и обновляется с помощью Flyway.

### Мероприятия

Мероприятие содержит основную информацию о событии, статус, владельца и набор полей регистрационной формы.

Поддерживаются статусы:

```
OPEN
CLOSED
CANCELLED
```

В текущем пользовательском сценарии используются `OPEN` и `CANCELLED`.

При отмене мероприятия запись `Event` не удаляется. Статус меняется на `CANCELLED`, при этом существующие регистрации и ответы пользователей сохраняются.

Создать мероприятие с датой начала в прошлом нельзя.

Статус `CLOSED` зарезервирован для дальнейшего развития жизненного цикла мероприятия, например для завершившихся событий.

### Регистрации

Один пользователь может зарегистрироваться на одно мероприятие только один раз.

Если у мероприятия задано ограничение `capacity`, Backend проверяет количество уже существующих регистраций перед созданием новой.

Регистрация разрешена только для мероприятия со статусом `OPEN`.

Все поля регистрационной формы в текущей версии являются текстовыми и обязательными.

При отмене своей регистрации запись `Registration` удаляется. Связанные `RegistrationAnswer` удаляются через `ON DELETE CASCADE`.


### Идентификация пользователя

Мероприятия и регистрации связаны с идентификатором пользователя MAX (`maxUserId`).

Mini App передает идентификатор текущего пользователя в HTTP-заголовке:

```text
X-Max-User-Id
````

Backend получает этот идентификатор на уровне HTTP-контроллеров и передает его в бизнес-логику как `maxUserId`.

`GET /api/events/{eventId}` является публичным и не требует `X-Max-User-Id`.

В текущей версии Backend доверяет значению `X-Max-User-Id` и не проверяет его подлинность по подписанным данным MAX. Это ограничение текущего MVP.

## Внешние сервисы и интеграции

### MAX

MAX используется как основная среда взаимодействия с продуктом.

Проект использует MAX для:

- работы чат-бота;
- запуска Mini App;
- идентификации пользователя;
- открытия конкретного мероприятия;
- распространения мероприятий между пользователями.

Mini App получает идентификатор пользователя из данных запуска MAX и передает его Backend API в HTTP-заголовке `X-Max-User-Id`.

В текущем MVP Backend не проверяет подлинность переданного идентификатора по подписанным данным MAX.


## Переменные окружения

Пример конфигурации находится в `.env.example`.

Для запуска проекта необходимо создать `.env`:

```bash
cp .env.example .env
````

После этого необходимо заполнить значения:

```
DB_PASSWORD=
BOT_TOKEN=
WEBHOOK_SECRET=
```

- `DB_PASSWORD` - пароль PostgreSQL;
- `BOT_TOKEN` - токен MAX Bot;
- `WEBHOOK_SECRET` - секрет webhook MAX Bot.

Имя базы данных `eva` и пользователь PostgreSQL `danil` заданы в `docker-compose.yml`.

Рабочие токены, пароли и другие секреты не хранятся в Git.

## Используемые порты

Сервисы приложения доступны на VPS только через loopback-интерфейс:

- `127.0.0.1:8080` - Java Backend;
- `127.0.0.1:8081` - MAX Bot;
- `127.0.0.1:8082` - Mini App.

PostgreSQL доступен только внутри Docker-сети и напрямую на порт хоста не публикуется.

Внешний HTTP/HTTPS-трафик принимает Nginx на портах `80` и `443` и проксирует запросы на соответствующие сервисы.

## Остановка проекта

Остановить и удалить контейнеры проекта:

``` bash
docker compose down
```


Данные PostgreSQL при этом сохраняются в Docker volume `postgres_data`.

Если требуется только остановить контейнеры без их удаления:

``` bash
docker compose stop
```

## Повторный запуск

После остановки:

``` bash
docker compose up -d
```

При необходимости повторной сборки образов:

``` bash
docker compose up -d --build
```

PostgreSQL использует именованный Docker volume `postgres_data`, поэтому данные сохраняются между обычными остановками и перезапусками контейнеров.

Удаление volume, например командой `docker compose down -v`, приведёт к удалению данных PostgreSQL.


## Тестовые данные

### Проверка MVP

Для проверки MVP тестовое мероприятие создаётся через обычный пользовательский сценарий в Mini App.

Пример:

```text
Название: Субботник
Описание: Уборка парка
Место: Новосибирск
Количество мест: 20

Поля регистрационной формы:
1. ФИО
2. Телефон
```

После создания мероприятие получает собственный `eventId`, а поля регистрационной формы — собственные `fieldId`.

Для проверки регистрации другой пользователь открывает созданное мероприятие и заполняет регистрационную форму, например:

```
ФИО: Иван Иванов
Телефон: +79990000000
```

Таким образом, данные для проверки основного пользовательского сценария создаются средствами самого приложения.

### Проверка API

Для воспроизводимой проверки собственного API используется файл [`test-data.json`](test-data.json).

В нём заданы:

- тестовый организатор с `X-Max-User-Id: 1001`;
- тестовый участник с `X-Max-User-Id: 1002`;
- данные тестового мероприятия;
- тестовый ответ регистрационной формы.

Идентификаторы мероприятия и полей формы заранее не фиксируются: они создаются сервером во время проверки и используются последующими запросами из [`DATA-API.yaml`](DATA-API.yaml).

*Тестовые значения `1001` и `1002` являются синтетическими идентификаторами для технической проверки API и не соответствуют реальным аккаунтам MAX.*

## Проверка основного сценария

1. Открыть EVA Bot в MAX.
2. Открыть Mini App.
3. Создать новое мероприятие:
    - указать основные параметры;
    - добавить поля регистрационной формы.
4. Сохранить мероприятие.
5. Открыть созданное мероприятие и скопировать ссылку на него.
6. Передать ссылку другому пользователю MAX (организатор также может зарегистрироваться на свое событие).
7. Открыть мероприятие по ссылке.
8. Заполнить регистрационную форму и отправить регистрацию.
9. Проверить, что регистрация успешно создана.
10. Открыть список своих регистраций и убедиться, что мероприятие присутствует в нем.
11. Отменить регистрацию.
12. Убедиться, что после отмены регистрация больше не отображается.

## Примеры ожидаемого поведения

### Создание мероприятия

После успешного создания Backend возвращает объект мероприятия с его идентификатором, статусом и регистрационной формой.

Пример:

```json
{
  "id": 1,
  "title": "Субботник",
  "description": "Уборка парка",
  "startsAt": "2026-10-10T10:00:00Z",
  "endsAt": "2026-10-10T14:00:00Z",
  "location": "Новосибирск",
  "capacity": 20,
  "status": "OPEN",
  "formFields": [
    {
      "id": 1,
      "label": "ФИО",
      "position": 0
    },
    {
      "id": 2,
      "label": "Телефон",
      "position": 1
    }
  ]
}
```

Полный контракт ответа описан в [`openapi.yaml`](openapi.yaml).

### Регистрация пользователя

Пользователь заполняет поля регистрационной формы и отправляет регистрацию.

После успешной регистрации Backend возвращает данные созданной регистрации.

Пример:

```json
{
  "id": 1,
  "eventId": 1,
  "registeredAt": "2026-09-20T12:02:37Z"
}
```

### Повторная регистрация

Если пользователь уже зарегистрирован на мероприятие, Backend возвращает HTTP `409 Conflict`.

```json
{
  "code": "ALREADY_REGISTERED",
  "message": "User is already registered"
}
```

### Ошибка данных формы

Если пользователь отправляет некорректную регистрационную форму, Backend возвращает HTTP `400 Bad Request`.

Пример:

```json
{
  "code": "INVALID_REGISTRATION_FORM",
  "message": "Wrong number of answers"
}
```

### Отмена регистрации

После успешной отмены регистрации Backend возвращает:

```text
204 No Content
```

После удаления пользователь может зарегистрироваться на мероприятие снова.

### Несуществующее мероприятие

При запросе неизвестного `eventId` Backend возвращает HTTP `404 Not Found`.

```json
{
  "code": "EVENT_NOT_FOUND",
  "message": "Event with id 999999 not found"
}
```

## Известные ограничения

Текущая версия MVP имеет следующие ограничения:

- поддерживаются только текстовые поля регистрационной формы
- все поля регистрационной формы обязательны
- редактирование созданного мероприятия не поддерживается
- история отмененных регистраций не сохраняется
- автоматический перевод завершившихся мероприятий в статус `CLOSED` не реализован
- Backend принимает `X-Max-User-Id` от Mini App без проверки его подлинности по подписанным данным MAX
